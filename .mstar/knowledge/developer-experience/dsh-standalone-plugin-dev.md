# Standalone dsh plugin development (verified recipe)

## Context

dsh (DeepSeek Harness) is Cordis-based: a plugin is a module exporting `apply(ctx)`, shipped as an npm bundle declaring a dsh.bundle manifest pointing at a `cordis.patch.yml`; the patch inserts loader rows (`- insert: - id: <row> name: <package>`). Users install with `dsh plugin --profile <name> add <spec>`.

The blocker for out-of-tree development: the `@deepseek-ai/dsh-*` packages are **private (not on npm)** — dev-time typecheck/build needs them locally, while runtime resolution comes from the dsh installation itself (two-anchor bundle resolution: installation first, then profile dir; a flat fallback under $DSH_HOME/profiles/node_modules makes every in-box package Node-resolvable from any profile via parent-walk). Runtime imports therefore belong in **peerDependencies**.

## Guidance

1. **Committed files stay path-free.** All machine-local paths live only in gitignored `dev/`, generated by a committed path-free `scripts/dev-link.mjs` (`DSH_SOURCE=<path> pnpm dev:link`, default sibling `../dsh-private`).
2. **The dev overlay is a shim package per dsh package, not a symlink.** Each dev/<pkg>/ has a `package.json` with main: './index.js' and a **top-level `types` field pointing at the real <abs>/lib/types/index.d.ts** (an index.d.ts re-export of the abs d.ts fails with TS2846); the shim index.js re-exports <abs>/lib/index.js. **Never symlink the real dsh package dirs** — their own node_modules split the `cordis` module identity and silently kill every `declare module 'cordis'` augmentation (ctx.sessions / ctx.agents / ctx.llm / the session event surface vanish from types).
3. **`pnpm-workspace.yaml`**: `packages: [dev/*]` + `linkWorkspacePackages: true` (**required** — without it pnpm 404s on the private ranges).
4. **`cordis` must also come from the overlay** (single module identity for augmentations). `moduleResolution: bundler` is required (cordis's published d.ts has extensionless relative imports; `node16` unusable).
5. **Build with `prepack`, never `prepare`.** `prepare` runs inside the profile's pnpm install where devDeps are absent. `prepack` runs at `pnpm pack` time; the tarball then contains only `lib/` + the patch + manifest (gitignored `dev/` never enters the package `files`).
6. **Install smoke without touching the real installation**: DSH_HOME=/tmp/dsh-home dsh plugin --profile <scratch> add <tarball> then `dsh --profile <scratch> --dump-config` (row present, 0 stderr). Runtime resolution of extra deps (e.g. `schemastery`) succeeds via the flat fallback; declare them as peers for correctness.
7. **Cordis inject service names are plural**: `sessions`, `agents`, `llm`, `commands` (singular names leave the plugin PENDING forever — a silent runtime no-op that `--dump-config` cannot catch). `commands` should be injected conditionally (`ctx.inject(['commands'], ...)`) to keep headless assemblies unaffected.
8. **`skipLibCheck: true` may be needed**: the dsh-llm retry-policy.d.ts pulls the vendored schemastery (`declare global`) colliding with a registry copy; the dsh repo itself builds with this setting.

## Why This Matters

The naive approaches all fail in confusing ways: `file:` devDeps commit local paths and shadow the real packages; tsconfig `paths` to the flat fallback typecheck-only and split the runtime cordis identity; symlinks silently destroy type augmentations. The verified overlay keeps committed files portable while preserving a single module identity.

## When to Apply

Any standalone dsh plugin repo (this repo is the reference implementation: `dsh-advisor`). For plugins developed inside the dsh monorepo, none of this applies.

## Examples

- Working overlay + probe + smoke tests: architect-verified in the KD-1 scratch (evidence of record) and reproduced in this repo (T1 + T8 install smoke: `pnpm dev:link` → `pnpm install` → `tsc --noEmit` → `pnpm pack` → DSH_HOME=/tmp/... dsh plugin add → `--dump-config` row present; boot probe reached `MISSING_CREDENTIAL`, proving module load).
